# Оформление сделки Nurzaman

Форма заявки + список + экспорт в Excel, с серверным модулем автоматического
распознавания ID-документов (паспорт / ID-карта КР), заменяющим ручное
копирование через Google Lens/Live Text.

## Запуск

```bash
npm install
cp .env.example .env   # заполнить при необходимости
npm start               # http://localhost:3000
```

Тесты: `npm test`.

По умолчанию `OCR_PROVIDER=mock` — распознавание работает без внешних
запросов и ключей (удобно для разработки/демо). Для реального провайдера
см. ниже.

Учётные записи компаний не создаются через API (см. "Мультиарендность"
ниже). При самом первом запуске сервер сам заводит стандартный набор
компаний и один раз печатает пароли в консоль/лог (см. `ensureSeeded()` в
`server/src/server.js`) — сохраните их сразу. Тот же результат можно
получить вручную:

```bash
npm run seed:companies   # создаёт учётки, пароли выводятся в консоль один раз
```

## Развёртывание в интернете, чтобы заходить откуда угодно

Локально (`npm start`) приложение доступно только на этом компьютере. Чтобы
заходить с телефона, из дома, с любого другого места — нужен хостинг.
Рекомендуемый вариант для старта — **Render.com** (есть бесплатный тариф,
деплой прямо из этого GitHub-репозитория, ничего не нужно настраивать на
своём компьютере):

1. Зарегистрируйтесь на [render.com](https://render.com) и подключите
   GitHub-аккаунт, где лежит этот репозиторий.
2. **New +** → **Blueprint** → выберите репозиторий — Render найдёт
   `render.yaml` в корне и предложит создать сервис по нему.
3. Проверьте план: `render.yaml` включает платный постоянный диск ($ от
   ~1 ГБ/мес) — **это обязательно**, иначе весь реестр приказов и сделки
   будут стираться при каждом обновлении сервиса. Без диска подойдёт
   только чтобы посмотреть интерфейс, не для реальной работы.
4. После деплоя откройте **Logs** в панели Render — там будут напечатаны
   логины и пароли автоматически созданных учётных записей компаний
   (см. выше) — сохраните их, повторно они не покажутся.
5. Заходите по адресу, который выдаст Render (вида
   `https://nurzaman-deal-form.onrender.com/login.html`), с любого
   устройства.

Альтернативы: **Railway.app** — тот же принцип (деплой из GitHub, но
конфиг `render.yaml` он не использует — задайте Build/Start команды
вручную: `npm install` / `npm start`, и подключите volume на
`server/src/data`); свой VPS — Node.js + процесс-менеджер (`pm2` или
systemd-юнит) + постоянный диск по умолчанию есть.

## Мультиарендность — одна учётка = одна компания

Приложение обслуживает несколько компаний одним сервером, но данные каждой
компании (сделки, реестр приказов, файлы сканов) полностью изолированы —
у каждой компании собственный логин/пароль и собственное хранилище,
физически отдельное от других компаний:

- **Вход**: `POST /api/login` (логин + пароль) заводит сессию и
  устанавливает httpOnly-cookie (`server/src/routes/auth.js`,
  `server/src/auth/sessions.js`). Пароли хранятся только в виде
  scrypt-хэша с индивидуальной солью (`server/src/auth/passwords.js`) —
  сам пароль нигде не сохраняется.
- **Учётные записи** заводятся скриптом `npm run seed:companies`
  (`server/scripts/seedCompanies.js`), не через API/UI — выдача доступа
  новой компании требует организационного решения, а не самостоятельного
  действия пользователя приложения. Пароли выводятся в консоль один раз
  при создании; если пароль забыт, учётку нужно пересоздать (в текущей
  версии скрипта — вручную заменить запись в `companies.json`).
- **Каждый API-роут с данными** (`/api/deals*`, `/api/orders*`) требует
  сессию (`requireAuth` в `server/src/middleware/auth.js`) и работает
  только с данными компании из этой сессии (`req.company.id`) — компания A
  не может увидеть, отредактировать или отменить приказ компании B, даже
  зная его id (проверено тестами, см. `server/test/ordersRegistry.test.js`,
  кейс "companies have fully isolated numbering...").
- **Хранилище** физически разделено по компаниям:
  `server/src/data/deals/<companyId>.json`,
  `server/src/data/orders/<companyId>.json`,
  `server/src/data/orders-files/<companyId>/...` — у компании нет доступа
  к чужим файлам даже теоретически (структура путей это исключает).
- **Нумерация приказов** ведётся отдельно на компанию — `MAX(number)+1`
  считается внутри реестра конкретной компании, поэтому у разных компаний
  спокойно существуют, например, свои собственные "приказ №1".

**Ограничение MVP**: сессии хранятся в памяти процесса
(`server/src/auth/sessions.js`) — перезапуск сервера разлогинивает всех
пользователей. Для эксплуатации с несколькими инстансами сервера сессии
нужно вынести во внешнее хранилище (Redis и т.п.) — как и мьютекс
нумерации приказов (см. ниже), это тот же класс ограничения "работает
только для одного процесса Node".

## Архитектура распознавания (см. ТЗ, п.5)

```
Браузер (фото, сжатое на клиенте)
  → POST /api/scan-id (multipart, сессия компании через cookie)
    → OCR-провайдер (ключ только в переменных окружения сервера, .env)
    → парсинг текста в {docNumber, pin, fullName}
    → валидация формата + порог confidence
  → JSON клиенту → автозаполнение полей формы (редактируемых, с пометкой)
```

Код:
- `server/src/routes/scanId.js` — эндпоинт, таймаут 5с, никогда не роняет форму.
- `server/src/ocr/provider.js` — абстракция провайдера (переключение через `OCR_PROVIDER`).
- `server/src/ocr/yandexVisionProvider.js`, `server/src/ocr/mockProvider.js` — реализации.
- `server/src/ocr/parseIdText.js` — разбор сырого текста OCR в поля документа.
- `server/src/validation.js` — валидация ПИН (14 цифр) и номера ID-карты.
- `server/src/utils/ocrLog.js` — логирование запросов к OCR без сохранения фото.

## Решение по OCR-провайдеру (ТЗ, п.6) — ЗАФИКСИРОВАНО, но требует проверки перед продом

**Выбран Yandex Vision OCR** как стартовая реализация:
- хорошо читает кириллицу, доступен в регионе;
- это **общий** OCR, не заточенный под ID-документы — структура полей
  восстанавливается собственным парсером (`parseIdText.js`), а не приходит
  готовой из провайдера.

Перед вводом в эксплуатацию нужно:
1. Прогнать реальные тестовые образцы паспорта/ID-карты КР через Yandex
   Vision и уточнить/расширить regex в `parseIdText.js` (сейчас это базовые
   эвристики: 14-значное число для ПИН, метка `ID №`/`№` для номера документа).
2. Уточнить фактический формат номера ID-карты КР (буквенно-цифровой,
   длина) — текущий `DOC_NUMBER_REGEX` в `validation.js` (6–12 символов
   A-Z0-9) — это допущение, не проверенный факт.
3. Если точность на MRZ/полях окажется недостаточной — рассмотреть переход
   на специализированный ID-SDK (Regula / Smart Engines / Microblink).
   Архитектура это позволяет: реализовать новый класс с методом
   `scan(imageBuffer)` в `server/src/ocr/` и подключить в `provider.js`,
   остальной код (валидация, роут, фронтенд) не меняется.

Провайдеры Google Document AI / AWS Textract сознательно не выбраны —
данные уходили бы на сервера вне СНГ (см. риск ниже).

## ⚠️ Требует согласования с юристом Nurzaman ДО запуска в эксплуатацию (ТЗ, п.7)

Это не техническое, а юридическое/организационное решение — код ниже
подготовлен так, чтобы его можно было включить, но параметры **не
установлены произвольно разработчиком**:

1. **Передача фото документа стороннему OCR-провайдеру, сервер которого
   физически вне Кыргызстана** — допустимость по Закону КР «О персональных
   данных» должна подтвердить юридическая служба до включения
   `OCR_PROVIDER=yandex` в проде.
2. **Срок хранения исходного фото.** Текущая реализация **не сохраняет
   исходное фото вообще** — буфер держится только в памяти процесса на
   время одного запроса к `/api/scan-id` и никогда не пишется на диск/в БД
   (см. `multer.memoryStorage()` в `scanId.js`). Переменная
   `ID_PHOTO_RETENTION_HOURS` в `.env.example` зарезервирована на случай,
   если бизнес решит временно кэшировать фото для подтверждения менеджером
   — по умолчанию функциональность выключена, значение ни на что не влияет,
   пока такое кэширование не будет явно реализовано и согласовано.
3. **Согласие клиента на обработку фото документа** — реализовано как
   отдельный чекбокс `photoConsent`, отличный от `agreementConsent»
   («согласен с условиями приобретения»). Бэкенд (`routes/deals.js`)
   требует `photoConsent=true`, если в заявке заполнены `docNumber` или
   `pin`. Текст формулировки чекбокса в `public/index.html` — черновой,
   финальную формулировку должен утвердить юрист.

## Валидация результата (ТЗ, п.8)

- ПИН КР — ровно 14 цифр (`validatePin`), иначе поле не подставляется.
- Номер ID/паспорта — сверяется с эвристическим форматом (см. предупреждение
  выше), иначе поле не подставляется.
- `OCR_CONFIDENCE_THRESHOLD` (по умолчанию 0.8): если провайдер отдаёт
  confidence ниже порога — поля не подставляются вовсе, а не помечаются
  особым образом (осторожная трактовка "не подставлять при низкой
  уверенности"). Yandex Vision OCR в используемом эндпоинте
  `recognizeText` не возвращает единый confidence по документу — в этом
  случае решение принимается только по валидации формата.

## UX (ТЗ, п.9)

- Автоподставленные поля — жёлтая подсветка + текст «Распознано
  автоматически — проверьте» (`public/css/styles.css`, `.autofilled`).
- Пометка снимается сразу при ручном редактировании поля
  (`public/js/app.js`, обработчики `input`).
- Сохранение без просмотра — не блокируется. Флаги `docNumberConfirmed` /
  `pinConfirmed` выставляются в `true` только при реальном ручном
  редактировании поля менеджером, иначе уходят в заявку как `false`.
- Экспорт в Excel (`routes/deals.js`) подсвечивает жёлтым непроверенные
  поля и добавляет колонки «проверен менеджером» — оформитель договора
  сразу видит, что перепроверить.
- Сбой распознавания (таймаут/провайдер недоступен/плохое фото) — форма не
  блокируется, показывается «Не удалось распознать — введите вручную»;
  ручной ввод остаётся рабочим независимо от статуса OCR.

## Нефункциональные требования (ТЗ, п.10)

- Таймаут ответа `/api/scan-id` — 5 секунд (`REQUEST_TIMEOUT_MS` в
  `scanId.js`), при превышении — управляемая ошибка, а не зависание формы.
- Ошибки провайдера (недоступен, лимит) перехватываются и возвращают 502 с
  понятным сообщением, не роняя остальную форму/сервер.
- Логирование запросов к OCR — `server/src/utils/ocrLog.js`, пишет
  метаданные (id запроса, провайдер, длительность, исход), **без**
  содержимого фото.

## Реестр приказов — автоматическая регистрация и нумерация

Отдельный модуль (`server/src/orders/`, `server/src/routes/orders.js`,
`public/orders.html`) реализует ТЗ «Автоматизированная система регистрации
и нумерации приказов». Страница доступна по `/orders.html` (ссылка
«Реестр приказов →» на главной странице).

Архитектура (ТЗ п.12):

```
Фото (сжатое на клиенте)
  → POST /api/orders/scan — OCR + разбор полей (дата/вид/ФИО/орг-я/№)
  → сверка с реестром + проверка дублей (без записи в реестр)
  → пользователь проверяет/исправляет поля на странице
  → POST /api/orders/confirm — здесь, и только здесь, присваивается номер
  → файл переносится из временного хранилища в постоянное
  → номер возвращается пользователю
```

Регистрация двухэтапная (scan → confirm) намеренно: номер нельзя
присваивать до того, как пользователь увидел распознанные данные — иначе
неверно распознанные поля попадали бы в реестр необратимо (ТЗ п.5.4,
номера не меняются после присвоения).

### Первичная загрузка старых приказов (ТЗ п.3)

`POST /api/orders/bulk-scan` принимает сразу несколько фото, распознаёт
каждое, сортирует по распознанной дате и возвращает таблицу предпросмотра
с *предлагаемыми* номерами — они не резервируются. Только после
`POST /api/orders/bulk-confirm` (пользователь подтвердил порядок и
исправил поля) номера присваиваются атомарно одним проходом
(`registry.registerBulk`).

### Нумерация и защита от конфликтов (ТЗ п.5)

`server/src/orders/registry.js` хранит реестр в JSON-файле
(`server/src/data/orders.json`, не коммитится) и вычисляет следующий номер
как `MAX(number) + 1`. Все операции, присваивающие номер, сериализуются
через промис-мьютекс (`withLock`) — это исключает гонку, когда два
одновременных `await` внутри Node "переплетаются" и вычисляют один и тот
же следующий номер. **Ограничение**: мьютекс работает только в пределах
одного процесса Node. Для эксплуатации с несколькими инстансами сервера
(балансировка нагрузки) этого недостаточно — понадобится БД с
транзакциями/уникальным индексом на `number` (например, Postgres с
`SELECT ... FOR UPDATE` или сиквенсом). Замена хранилища не требует
переписывать роуты — `registry.js` уже изолирует эту логику.

Отмена приказа (`POST /api/orders/:id/cancel`) не удаляет и не
переиспользует номер — меняется только `status` (ТЗ п.5.4).
Правки (`PATCH /api/orders/:id`) не могут изменить `number` — поле
исключено из списка редактируемых в `registry.updateEntry`, а все правки
пишутся в `history` записи.

### Электронный реестр как таблица (ТЗ п.4) — решение по хранилищу

ТЗ называет Google Sheets/Excel Online предпочтительным вариантом. Прямая
интеграция с Google Sheets API требует организационного решения — учётной
записи сервиса и доступа к конкретной таблице компании — которое не
принимается разработчиком в одиночку (сравнимо с решением по OCR-
провайдеру, см. выше). Поэтому первый этап реализован так, чтобы
результат совпадал с требованием "реестр — электронная таблица" без
внешних учётных данных:

- `GET /api/orders/export` отдаёт актуальный реестр как `.xlsx`
  (аналогично экспорту сделок), с подсветкой записей `needs_review`.
- Структура данных (`registry.js`) уже соответствует полям из ТЗ п.4, так
  что при выборе конкретного Google Sheets/Excel Online аккаунта
  синхронизацию можно добавить как отдельный шаг записи после
  `registerOne`/`registerBulk`, не меняя остальной модуль.

### Распознавание полей приказа и порог уверенности (ТЗ п.6, п.8)

`server/src/orders/parseOrderText.js` разбирает сырой текст (тот же общий
OCR-провайдер, что и для ID-документов, см. `ocr/provider.js`) в дату, вид
приказа, ФИО, организацию и уже указанный номер — эвристиками/regex,
аналогично `parseIdText.js`. Если дата или вид приказа не распознаны (или
провайдер вернул confidence ниже `OCR_CONFIDENCE_THRESHOLD`), запись
получает статус `needs_review` вместо того, чтобы придумывать значения —
пользователь должен исправить поля вручную перед подтверждением.

Демо-провайдер (`OCR_PROVIDER=mock`) возвращает текст, рассчитанный на
формат ID-документа (см. выше), а не приказа — при локальной разработке
без реального OCR-ключа сканирование приказа ожидаемо всегда попадает в
`needs_review`. Это корректное поведение модуля ("не распознано — не
угадывать"), а не баг мока; для демонстрации автозаполнения нужен реальный
`OCR_PROVIDER=yandex` с тестовым фото приказа.

### Проверка дублирования (ТЗ п.7)

`server/src/orders/duplicateCheck.js` сравнивает новый приказ с уже
зарегистрированными (кроме отменённых/недействительных) по дате, ФИО, виду
приказа (точное совпадение) и краткому содержанию (похожесть по словам,
коэффициент Жаккара). Порог предупреждения — `ORDER_DUPLICATE_THRESHOLD`
(по умолчанию 0.7). При превышении порога `POST /api/orders/scan`
возвращает список кандидатов с оценкой и тем, что совпало; окончательное
решение (зарегистрировать как новый / открыть существующую запись /
отменить) — за пользователем на странице `/orders.html`.

### Хранение фото (ТЗ п.9)

Двухэтапно, как и сама регистрация: до подтверждения файл лежит во
временном хранилище (`server/src/data/orders-tmp/`, не коммитится) под
случайным токеном — номер ещё не известен. После подтверждения
(`storage.moveToPermanent`) файл переносится в
`server/src/data/orders-files/<companyId>/<год>/№<номер>-<uuid>.<ext>`.
Неподтверждённые сканы (пользователь закрыл вкладку и не подтвердил)
удаляются по TTL (`ORDER_SCAN_TTL_MINUTES`, раз в час, см. `server.js`).

## Что осознанно не реализовано / оставлено как заглушка

- Вход — логин/пароль на компанию с сессией в памяти процесса (см.
  "Мультиарендность" выше), не полноценный SSO с ролями внутри компании
  (все пользователи компании делят одну учётку). Для прод-эксплуатации
  внутри Nurzaman, если нужен персональный вход сотрудников, а не только
  разделение по компаниям, — заменить на реальную систему входа
  сотрудников поверх текущей модели компаний.
